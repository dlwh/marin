# Shuttle ABI 14 ordinary-JAX Contract VJP slice

## Status

Red-first implementation plan. No GPU, PTX assembly, numerical, cache, or
performance evidence has been collected for this slice.

## Objective

Advance the ordinary-JAX GPU path from one `Contract -> BF16 Map` forward
region to one connected JAX-VJP region. The first admitted graph is the
backward function generated by
`jax.jit(jax.vjp(matmul)[1]).lower(...).compiler_ir(StableHLO)`:

```text
BF16 lhs, rhs, and output cotangent
  -> exact BF16-to-FP32 conversion Maps
  -> two rank-two Contracts with FP32 accumulation
  -> one transpose Map and explicit FP32-to-BF16 Maps
  -> BF16 lhs and rhs gradients
```

Selection remains structural. Module/function names, fixture IDs, shapes,
digests, and workload labels do not participate in admission or dispatch.

## Closed initial boundary

- One connected Shuttle region containing only `shuttle.contract` and
  `shuttle.map` operations. Every operation must be connected to a Contract
  through SSA producer/consumer edges. Admission does not inspect operation
  counts; the pinned backward fixture happens to contain two Contracts and
  eight Maps.
- Static rank-two external BF16 tensors and rank-two internal BF16/FP32
  tensors. External results remain BF16.
- Contract inputs have the same element type, BF16 or FP32; the accumulator
  and result are FP32.
- Exactly one contracting dimension, no batching dimensions, default
  precision, and projected-permutation indexing maps. The two parallel and one
  reduction dimensions are derived from the maps, not assumed to be M/N/K in
  fixed operand positions.
- Map result indexing is identity. Input maps may be identity, broadcast, or a
  projected permutation already supported by the generic Map emitter. Scalar
  bodies remain restricted to the existing closed FP32 arithmetic and explicit
  BF16 conversion surface. Unsupported transcendental Maps fail closed.
- Exact default tuning. Both SOURCE_ORDERED and FAST are admitted. Each
  Contract independently uses ABI 13's policy-bound realization:
  serial ascending `fma.rn.f32` for SOURCE_ORDERED and lane-strided warp-32
  accumulation plus the fixed 16/8/4/2/1 shuffle tree for FAST.
- Existing transport/device/invocation/bundle schemas and typed-FFI target stay
  unchanged. Pipeline ABI becomes 14 so options and persistent cache identity
  rotate.

## Red-first gates

1. The pinned ordinary-JAX matmul-VJP fixture must pass the full GPU replacement
   pipeline under both policies and erase all StableHLO/Shuttle sidecars into
   the fixed API-v4 custom call.
2. Public serialization and `GpuExecutable::Load` must expose exactly the
   source-derived task/buffer graph, two Contract kernels, three operands, two
   results, policy-bound distinct roots, and immutable structural dependencies.
3. Contract code generation must derive both operand addresses from affine
   indexing maps. Tests cover canonical K-inner, contracting-dimension-zero,
   and rhs-contracting-dimension-one forms with non-square shapes.
4. FP32 internal Contract inputs must load FP32; BF16 Contract inputs must load
   BF16 and widen. Transpose Maps must preserve their projected input map.
5. Fail closed on disconnected regions, live FP32 outputs, mixed Contract
   input dtypes, batching, multiple contracting dimensions, nondefault
   precision/tuning, nonidentity Map result indexing, unsupported scalar ops,
   and adjacent pipeline ABI 13/15.
6. Existing ABI 13 single-Contract SOURCE_ORDERED/FAST behavior remains green
   except for the intentional global pipeline-ABI/cache-identity rotation.

Composed forward-plus-backward execution is the next slice. A plain composed
matmul currently forms separate forward and backward Shuttle regions, so
coalescing regions versus emitting multiple custom calls must be decided
explicitly before claiming composed execution.

## Evidence boundary

Local MLIR/native/Python tests can prove structural admission, byte/root
closure, PTX text derivation, public descriptor behavior, and ABI separation.
They cannot prove PTX assembly, H100 execution, ordinary-JAX numerical parity,
fresh-process persistent-cache reuse, or performance. Those require a later
sealed architecture-conforming H100 subject built from the exact reviewed tip.
